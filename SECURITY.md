# Security

## Reporting a vulnerability

Do **not** open a public GitHub issue for security vulnerabilities. This avoids disclosing exploitable details before a fix is available.

To report a vulnerability:

1. Email the maintainer at `security@example.com` (replace with real contact before publishing).
2. Include a description of the issue, reproduction steps, and your assessment of impact.
3. You will receive an acknowledgement within 48 hours and a resolution timeline within 5 business days.

Responsible disclosure is appreciated. Please allow a reasonable time for a fix to be developed and deployed before making any details public.

## Security posture summary

### Authentication and authorisation

| Control | Implementation |
|---|---|
| Staff authentication | JWT, HS256, 8-hour expiry, signed with a server-side secret |
| Algorithm pinning | `algorithms: ['HS256']` on every `jwt.verify()` call — protects against `alg: none` and algorithm-confusion attacks |
| Password storage | bcrypt, cost factor 12 — never plaintext |
| Timing-safe login | Unknown usernames are compared against a dummy bcrypt hash, so response time does not reveal whether a username exists |
| Required secret at startup | Server refuses to boot if `JWT_SECRET` is missing |
| Public vs. staff actions | Anyone can create reports (zero friction for the core workflow); only authenticated staff can edit, delete, or view reporter PII |

### PII handling

`reporterIdCard` (Thai 13-digit national ID) is:
- Stored in the database (the organisation may need it for follow-up)
- **Never** returned to unauthenticated API callers — stripped in `server.js#redactForPublic()`
- Also redacted in the `POST /api/points` creation response, even for the submitting caller

The `STAFF_ONLY_FIELDS` array in `server.js` is the single location to audit or extend PII redaction.

### File uploads

| Control | Implementation |
|---|---|
| MIME type whitelist | JPG, PNG, WEBP, GIF, PDF only |
| Extension whitelist | Same set; both MIME and extension must match |
| On-disk filename | UUID-generated by the server — never derived from user input (prevents path traversal and overwrite attacks) |
| File size limit | 10 MB per file, 5 files per request |
| Served as static files | `/uploads/` is served by Express static middleware with `Content-Disposition: inline`; files are never executed |
| Orphaned file cleanup | Files written by Multer before a validation failure are deleted before the 400 response is sent |

### Rate limiting

| Scope | Window | Limit | Purpose |
|---|---|---|---|
| All `/api/` routes | 15 min | 300 req | General protection; mitigates PII scraping |
| `POST /api/auth/login` | 15 min | 10 req | Slows credential-guessing attacks |
| `POST /api/points` | 15 min | 60 req | Reduces spam on the public write endpoint |

### HTTP security headers

Helmet is configured with:
- `Content-Security-Policy`: restricts scripts, styles, images, and fonts to `self` and explicitly whitelisted CDNs (cdnjs for Leaflet, OSM/CartoCDN for map tiles, Google Fonts). No `unsafe-eval`.
- `Strict-Transport-Security` (HSTS): enforced by Helmet when `NODE_ENV=production`.
- `X-Frame-Options`: `SAMEORIGIN` — protects against clickjacking.
- `X-Content-Type-Options`: `nosniff`.
- `Referrer-Policy`, `Permissions-Policy`: Helmet defaults.

### Database

| Control | Implementation |
|---|---|
| Parameterised queries | All queries use SQLite's prepared-statement API — no string interpolation, no SQL injection surface |
| CHECK constraints | lat/lng bounds, null-island rejection, age range, ID card format — enforced at the database level independent of the API layer |
| Foreign keys | `PRAGMA foreign_keys = ON` — ensures `ON DELETE CASCADE` and referential integrity are enforced |
| WAL mode | Concurrent readers do not block behind writers; safe for multi-process access on one host |

## Known limitations

These are documented tradeoffs, not undiscovered issues:

**Single shared staff account.** There is one `admin` account with no per-user audit trail. Anyone with the credentials can edit or delete any report, and there is no record of who made which change. For a genuine multi-officer rollout, per-user accounts with an audit log are required.

**SQLite is not a multi-host database.** SQLite's WAL mode is safe for concurrent access from multiple processes on one host, but not across multiple hosts. A deployment with multiple application servers requires PostgreSQL. See [docs/database.md — PostgreSQL migration path](docs/database.md#postgresql-migration-path).

**No CSRF protection.** The app is a same-origin SPA and uses `Authorization: Bearer` headers (not cookies) for authentication, so CSRF does not apply to the authenticated API endpoints. If cookie-based auth is ever added, CSRF protection must be added at the same time.

**No audit log.** Edits and deletes are not logged with a before/after record. For a production deployment handling sensitive data, an append-only audit table should be added.
